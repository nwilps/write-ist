Module — a piece of the program, with a front door.
Seam — where you can change behaviour without editing the caller.
Deep — a lot of behaviour behind a small front door.
Leak — a caller has to know something that should stay inside.

Interface is everything a caller must know to use a module. Locality means a bug lives in one place. Leverage means one front door serves many callers. Shallow means the front door is almost as complicated as the inside.

Module · who is speaking

EDWARD (V.O.) (CONT'D) is Edward.

A scene heading starts him fresh. Action between two cues is a break. Add (CONT'D) only — never touch (V.O.) or (O.S.).

Typing still decides when: not while the caret is inside the cue.

Problem. Import walks the elements forward to add (CONT'D); typing walks the page backward and decides the same resumption a second time.

Solution. One rule over the element sequence says whether a cue resumes; import and typing both call it, and a name list can call it too.

  • Locality: the resume rule once
  • Leverage: import and typing
  • Name stripping stays shared
  • Tests share one table
  • Blank lines stay inside
  • Follows ADR-0026 and ADR-0029

Module · a writing day

One open of the file. The day line is written only after the manuscript is safe. A ledger failure never blocks leaving.

Tests use the stand-in folder. The real disk stays an adapter behind the seam.

Problem. Launch writes “opened” and “closed”; leaving a project opens the ledger a second time to write that day’s words and pages, and the tests never take that path.

Solution. One module hears launched, quit, and project closed, and it is the only thing that appends a line.

  • Locality: when a day is written
  • Leverage: three moments, one file
  • One open of the ledger
  • Close path becomes testable
  • Failure still never blocks
  • Follows ADR-0017

Module · names and headings

Read off the elements. Edward once, however many times the cue says EDWARD (V.O.).

Not built until you ask. The point is where it would live.

Problem. Name suggestions do not exist yet, and the obvious place to build them is a fresh scan beside the two walks that already know a cue.

Solution. When that slice starts, derive the list in one module from the element sequence — the same name a (CONT'D) cue already yields — and do not store it.

  • Locality: one derived list
  • Leverage: suggestions and (CONT'D)
  • No sidecar, no word bank
  • Waits for the slice 2 ticket

Not a contradiction of ADR-0029. It is that decision, given a module to live in. Building it before the ticket would be early.
